## 0. 중요한 것

룸 시스템의 송 / 수신 로직은
기존 `ClientManager` 기반 브로드캐스트에서 `Room` 기반 브로드캐스트로
**송신되는 범위만 달라진다.**

하지만,

- 메시지를 서버가 송 / 수신하는 도중에 룸이 폭파된다거나
- 입장하는 도중에 룸이 폭파된다거나
- 여러 클라이언트 세션이 동시에 입장한다거나
- 룸에 들어가려하는데 이미 룸이 폭파되어있다거나

하는 예외 처리가 대부분일 것 같다.. 힘들겠다..

여기서 중요한거!

`Room`의 물리적 소멸과 논리적 폐쇄는 다르다.

- 물리적 소멸 : `shared_ptr`에 의해서 일어남(어떤 `shared_ptr`도 해당 `Room`을 참조하지 않음)
- 논리적 폐쇄 : `shutting`에 의해서 일어남(`shutting == true`라면 해당 룸은 더이상 사용되면 안됨, 하지만 물리적으로 소멸됐다는건 아님)

5번 섹션인 문제 섹션에는 연속 문제라고 인용구가 있는 부분이 있는데,
말 그대로 기존 문제의 해결책을 생각해보면서 연속적으로 발생한 문제라는 뜻임.

결국 이제 두 단계로 분리된다.

- 송수신 로직 : Send / Recv Thread 관련
- 이벤트 로직 : 닉네임 시스템 / 룸 시스템 등

이 두 가지를 분리해서 생각해보자.

### 0-1. 불변식들

> 안지키면 큰일나는 사실들.

1. Manager에 없는 Client는 어떤 Room에도 없어야 한다.
2. Manager에 없는 Room을 Client가 참조하면 안 된다.
3. Client가 Room을 참조한다면 Room.members에도 Client가 있어야 한다.
4. Room.members에 Client가 있다면 Client도 그 Room을 참조해야 한다.
5. 한 Client는 최대 한 Room에만 존재해야 한다.
6. 삭제된 Client나 Room에는 이후 어떤 작업도 수행되면 안 된다.
7. 논리적 폐쇄된 Room에는 이후 어떤 새로운 작업도 수행되면 안 된다. 기존에 수행하던 작업은 수행될 수 있다.

```text
client.current_room == room
    ⇔
room.members contains client
```

이게 중요.

### 0-2. 구현 단계

1. **불변식과 정책을 지키며** 예외를 무시한 채 필요한 기능만 구현
2. 예외 처리(6. 예외 상황 목록 참조)
3. 룸 시스템을 완성한다면 `Echo Server.cpp`을

### 0-3. 정책

> 불변식과 별개로, 설계 도중에 한계 등으로 생긴 지켜야하는 사실들.

1. `Manager::rooms`의 상태를 바꾸거나 해당 목록을 사용해야하는 동작(5-6 참조)은 `Manager`를 통한다. (예 : 룸 생성 / 룸 삭제 / 입장 / 퇴장(이건 추상화 수준 맞추기 용))
2. 해당 룸의 상태를 바꾸지 않는 동작은 `Manager`를 통하지 않고 `Room`에서만 처리해도 된다.(예 : 브로드캐스트 등)
3. `shutting`을 바꾸는 동작은 1번 정책에서 예외이다.(`shutting`을 바꾸는 동작은 `Manager`를 통하든 안통하든 상관없다. 급한거니까.)(추가 : `shutting`은 `Room::Shutdown()` 함수에서만 일어난다. 그러므로 이 정책은 어느정도는 무효이다.)
4. 락을 잡는 순서는 무조건 `Manager::rooms_mutex` -> `Room::room_state_mutex` -> `ClientSession::current_room_mutex` 순서로 잡아 데드락을 사전에 예방한다.
5. 룸의 특정 `ClientSession`을 `Join` / `Leave`하는 권한은 오직 해당 `ClientSession`만 가진다.(아직 강퇴 기능 / 타인에 의한 퇴장 기능 없다는 이야기)
6. 룸 브로드캐스트 시, 이미 `shutting == true`가 되었다고 해도 해당 브로드캐스트는 전부 수행하고 해당 룸 브로드캐스트 함수를 종료한다.(계속 `shutting == true`를 검사하는 branch prediction 비용을 줄이기 위함)
7. `Room`에 대한 모든 상태 변경은(폐쇄 절차 포함) `Room::room_state_mutex` 안에서 배타적으로 일어난다.(5-1, 5-2, 5-3 등 많은 부분에 영향을 끼침.)

2. 룸 인원 / 모든 룸 정보 등 룸의 정보를 제공하는 기능

### 0-5. 현재 구현 해봄직한 기능들

## 1. 내가 생각한 구조

```text
             Manager
      ┌──────────────────┐
      │ Client 목록      │
      │ Room 목록        │
      └──────┬───────────┘
        shared_ptr 로 소유
     ┌───────┴────────────────────────────┐
     │                                    |
     ↓                                    ↓
 ClientSession                          Room
 ClientSession    weak_ptr로 상호 참조   Room
 ClientSession                          Room
```

### 1-1. Manager

(현 ClientManager)

- 모든 ClientSession 관리
- 모든 Room 관리
- Room 생성/삭제
- Client를 Room에 넣고 빼기
- 전체 브로드캐스트(이미 구현되어있는 기능임 이건)

이 객체에서 룸의 상태를 바꾸는 동작이 일어난다.

#### 필요한 동작

- Room 생성
- Room 삭제
- Room에 클라이언트 입장
- Room에서 클라이언트 퇴장
- 룸 브로드캐스트는 룸의 상태를 바꾸지 않으므로 없음

### 1-2. Room

- 자기 방에 속한 Client 목록만 관리
- Room 내부 브로드캐스트

이 객체에서 해당 룸의 상태를 바꾸지 않는 동작들이 일어난다.

#### 필요한 동작

- 해당 Room에 특정 멤버 추가
- 해당 Room의 특정 멤버 삭제
- 해당 Room 폐쇄 처리(`shutting.store(true)`)
- 해당 Room에 브로드캐스트

해당 Room에 특정 멤버 추가 / 삭제, 해당 Room 폐쇄 등의 룸의 상태를 바꾸는 동작은 `Manager`의 함수들을 통해서 일어남.
해당 Room에 브로드캐스트 하는 부분은 `ClientSession`의 `current_room` `weak_ptr`를 사용해서 일어남.

#### 룸은 ClientSession을 기반으로 만들자.

> 이건 현재 유명무실해졌음. 그냥 과거 아이디어로 치부하자.

- ClientSession처럼 ClientManager가 다룸
- 룸의 상태(살아있음 / 삭제됨)가 `closing` 변수같은 분류가 됨
  - 그 분류로 예외 처리도 가능함
- (만약 룸의 이름도 있다면) ClientSession의 nickname같은 처리를 할 수 있게 됨(현재는 룸의 이름은 구현할 생각 없음)
- 룸의 ID를 ClientSession처럼 데이터 레이스가 발생하지 않도록 발급하고,
그렇게 컨테이너에 넣어서 key-value 해시 테이블로 $O(1)$의 시간복잡도로 탐색 / 삽입 / 삭제 가능
  - 그리고 각 룸의 구분도 ClientSession처럼 RoomID로 가능

### 1-3. ClientSession

- Manager 참조
- 자신이 속한 Room 참조(현재는 단일 룸 구조로 할 생각)

여기서 해당 클라이언트에 대한 실질적 송 / 수신 및 기본적인 패킷 처리가 일어난다.

```cpp
        // Manager::rooms를 건들지 않으니 rooms_mutex를 잡을 이유 없음

        auto room_to_leave = client->GetRoom(); 
        if (room_to_leave == nullptr) { // 만약 이미 룸이 터진 경우(LeaveRoom() 함수 호출과 GetRoom() 함수 호출 사이에 룸이 터지면 이게 가능함)
            return false; // 어차피 룸이 터지면 ClientSession::current_room도 무효화되니까 이것만 해도 상관없음.
        }

        return room_to_leave->RemoveMember(client->GetSessionID());
    }
```

```cpp
class Room : public std::enable_shared_from_this{
private:
    std::unordered_map<SessionID, std::weak_ptr<ClientSession>> members;
    std::weak_ptr<Manager> manager_wp;
    uint64_t room_id;
    std::atomic<bool> shutting = false; // 이거 일반 bool 변수로 바꿔놔야함. 하지만 룸 종료 권한 관련 문제가 생길 경우 CAS 연산이 필요할 수 있기에 현행유지.
    std::mutex room_state_mutex; // 캡슐화(함부로 이 락 잡아서 발생하는 데드락 방지)
public:


    Room(uint64_t this_room_id, 
         std::shared_ptr<Manager> manager_sp) 
    : room_id(this_room_id), manager_wp(manager_sp) {
        
    }

    // 소멸자에서 Room 소멸 Logging
    ~Room() {
        LineLogger::GetInstance().WriteLog("[Room Deleted] The room has been closed. Room ID : ", room_id);
    }

    // 룸 초기화 전용 함수
    // 호출 시 해당 객체에 대한 shared_ptr로 호출함
    // 호출 주체 : Manager
    // 초기 멤버 추가 성공 / 실패에 따라 true / false를 반환한다.
    bool SetInitMember(std::shared_ptr<ClientSession> session_to_create) {
        if (!session_to_create) return false;
        
        SessionID id = session_to_create->session_id;
        
        std::lock_guard<std::mutex> lock(room_state_mutex);

        if (shutting.load()) return false;

        // 불변식 3, 4 만족(members에 추가 / current_room 참조가 둘 다 성공하거나 둘 다 실패함.) - 근데 이거 도중에 해당 룸이 날아가면 어떻게되냐? - 문제 없음. 5-1 참조
        session_to_create->SetRoom(shared_from_this()); // 이미 shared_ptr로 생성된 객체이므로 문제 없음!
        members[id] = session_to_create;
        return true;
    }

    // 초기화 후 다른 클라이언트가 해당 룸에 들어올 때 전용 함수
    // 호출 시 해당 객체에 대한 shared_ptr로 호출함
    // 호출 주체 : Manager
    // 멤버 추가 성공 / 실패에 따라 true / false를 반환한다.
    bool AddMember(std::shared_ptr<ClientSession> client) {
        if ((client == nullptr) || (client->GetRoom() != nullptr)) { // client가 유효하지 않거나 이미 다른 룸에 소속되어있는 경우
            return false;
        }

        SessionID id = client->session_id;

        std::lock_guard<std::mutex> lock(room_state_mutex); // shutting을 변경하려면 해당 락을 잡아야됨. 그래서.. (5-3 참조)

        if (shutting.load()) return false;

        // 여기도 불변식 3, 4 만족 - 같은 문제 공유
        client->SetRoom(shared_from_this());
        members[id] = client;
        return true;
    }

    // session_id를 받아 해당 session id의 클라이언트를 룸에서 제거하는 함수
    // 호출 시 해당 객체에 대한 shared_ptr로 호출함
    // 호출 주체 : Manager
    // 멤버 제거 성공 / 실패에 따라 true / false를 반환한다.
    bool RemoveMember(SessionID id){
        std::lock_guard<std::mutex> lock(room_state_mutex);

        if (shutting.load()) return false;

        auto it = members.find(id);
        if (it == members.end()) return false;

        if (auto client_sp = it->second.lock()) {
            if (client_sp->GetRoom().get() == this) { // 아직도 나를 가리킬 때만 ClientSession::current_room을 nullptr로
                client_sp->SetRoom(nullptr);
            }
        }
        // 해당 client 객체가 사라졌어도 별다른 처리를 하지 않는다.

        members.erase(it); // 이미 해당 객체가 사라졌어도 weak_ptr 지우기

        return true;
    }

    std::vector<std::weak_ptr<ClientSession>> GetMembers(){
        std::vector<std::weak_ptr<ClientSession>> snapshot;

        {
            std::lock_guard<std::mutex> lock(room_state_mutex);
            
            // 락 잡은 상태에서 shutting 플래그를 확인해서 Shutdown() 함수가 호출됐을 때 shutting == true를 놓칠 가능성 없앰
            // 다른 shutting 플래그 확인하는 부분에서도 이 논리로 락을 잡은 상태로 shutting 플래그를 확인함
            if (shutting.load()) { // 만약 룸이 논리적 폐쇄됐다면 빈 스냅샷 반환
                return snapshot;
            }

            snapshot.reserve(members.size()); // 미리 members의 크기 이상만큼 메모리를 할당받아서 추가적인 메모리 할당 최적화

            for (const auto& [id, session_ptr] : members) {
                snapshot.push_back(session_ptr);
            }
        }

        return snapshot;
    }

    // 해당 함수가 락을 잡아야 shutting이 true가 됨
    // 호출 주체 : Manager
    void Shutdown() {

        bool expected = false;

        std::lock_guard<std::mutex> lock(room_state_mutex);

        
        if (!shutting.compare_exchange_strong(expected, true)){ // 이미 다른 스레드가 shutting == true로 바꿨다면 해당 스레드는 shutdown 절차를 진행하지 않음(현재는 내가 이걸 아는게 CAS뿐이라 이걸로 구현해놓음.)
            return;
        }

        // CAS 연산으로, shutdown 절차를 진행할 책임을 처음으로 shutting = true로 바꾼 스레드에게 넘김.

        for (auto& [id, client_wp] : members) {
            if (auto client_sp = client_wp.lock()) {
                client_sp->SetRoom(nullptr);
            }
        }

        members.clear();
    }

    // 패킷과 송신자 ID를 받아 해당 룸에 대한 브로드캐스트를 수행하는 함수
    // 호출 시 해당 Packet에 대한 shared_ptr를 사용해서 호출함
    // 호출 주체 : ClientSession
    bool BroadcastThisRoom(std::shared_ptr<Packet> packet, const SessionID sender_id){

        // 스냅샷을 따서 브로드캐스트 중 세션이 입 / 퇴장하는 문제 해결
        std::vector members_snapshot = GetMembers();

        // shutting == true가 되어도 브로드캐스트는 끝까지 수행해야하기 때문에 shutting 체크를 하지 않음

        for(auto& client_wp : members_snapshot) { // 스냅샷이기 때문에 도중에 원본 members가 소멸해도 문제 없음

            // 중간에 shutting == true가 되더라도 메시지 전송(Send Queue에 Push)은 다 끝냄.
            if (auto client_sp = client_wp.lock()) { // weak_ptr를 기반으로 접근해서 도중에 세션이 사라지더라도 댕글링 포인터 문제가 발생하지 않음
                if (client_sp->GetSessionID() == sender_id) {
                    continue;
                }
                client_sp->SendQueuePush(packet);
            }
        }

        return true;
    }
};
```

### 5-2. Room이 폐쇄 상태일 때 들어가있는 클라이언트와의 연결은 어떻게 끊을까?(최종 결론 남)

제목이 곧 내용.

`shutting == true`고 `Room` 객체가 소멸될 때 `ClientSession::current_room`의 연결을 다 끊어줘야 함.
이건 앞에서 설명했듯이

- `shutting == true`인 룸에는 더이상 어떤 작업도 실행되지 않게 하고
- `Room` 객체의 소멸자에서 `members`의 `weak_ptr`로 각 `ClientSession` 객체를 참조해서 `current_room`을 `nullptr`로 바꾸는 식.

그래서 소멸자에서 각 `weak_ptr`로 각 `ClientSession::current_room`을 무효화하면 됨.

아 잠만 소멸자가 아니라 `Manager` 차원에서 호출하는 `Shutdown()` 함수를 만들자.
거기서 `current_room` 무효화도 하고.

- 이미 `ClientSession` 객체가 삭제된 경우에는 `weak_ptr`를 쓰기 때문에 없어진 `ClientSession`을 참조하는 문제가 없음(6번 불변식)
- `ClientSession` 객체가 살아있는 경우에는 무조건 `shared_ptr`을 통해 `ClientSession::current_room`과 `members[client]`가 연결되어있는 것이 보장되므로(5-1 참조)
문제가 없음.

5-3에서 확인한 것처럼 `Room::room_state_mutex`를 잡아야만 해당 룸 객체가 소멸되게 해서 `ClientSession::current_room`과 `Room::members[client]`를 바꾸는 연산은
타이밍에 따라 둘 다 성공 / 둘 다 실패하게 된다는 것이 보장됨.(문제 없음!)

---

> 연속 문제 1 : `current_room`의 동기화는 어떻게 진행할까?
> 해당 연속 문제는 해결 중. `shared_lock` 공부해야함.

근데 여러 `Room` 객체 말고도 유저의 입력으로 `current_room`이 바뀔 수 있는데..?

`Room` 객체(방 폭파) : 수동적
유저의 입력 : 능동적..

그래서 `current_room`에 대한 동기화가 필요할 듯.
읽기(해당 포인터로 역참조) / 쓰기(해당 포인터를 바꿈) 모두 공통된 락이 필요할 듯.

이게 왜 그러냐면,

- 해당 포인터로 `Room`을 참조하는 경우 : 도중에 다른 `Room`으로 바뀌면 안됨(데이터 레이스)
- 해당 포인터를 수정하는 경우 : 도중에 다른 `Room`으로 바뀌면 안됨(데이터 레이스), 수정하는 중에 읽으면 안됨(데이터 레이스)

이렇기 때문에..

이거 근데 어느정도 분리는 있어야할 것 같은데?

- 읽기 : 여러군데에서 가능
- 쓰기 : 여러군데에서 가능

이렇긴 해서..

근데

- 읽는 도중에는 쓰기를 하면 안됨
- 쓰는 도중에는 읽기 / 쓰기를 하면 안됨

이렇게 되어서, 읽기 / 쓰기 락을 구분해야함.

이거 `<mutex>` 헤더에 있는 것 같던데.. `std::shared_lock`이었나?

(**이건 아직 구현 예시에 미반영**)

> 이전 결론 : `shared_lock` 공부하고 이 문제를 다시 보자.
> 현재 결론 : 그냥 `mutex`를 쓰자.

괜히 설계 복잡해질 것 같아서,
읽기 / 쓰기 별도 락을 고려하지 않고
쓰기와 읽기 모두 `current_room`을 보호하는 뮤텍스를 하나 두자.

동시 읽기가 불가능해지겠지만,
`current_room`이 그렇게 많이 쓰이지도 않을 것 같고..

### 5-3. 폐쇄중인 `Room`에 접근할 때 `shared_ptr`가 이미 삭제되는 문제(해결됨)

이것도 매우 중요함. 5-1번 생각하다가 나온 문제임.

만약 `std::shared_ptr`를 들고 해당 `Room` 객체에 접근했는데, 도중에 `shutting == true`가 되어서
`Manager`의 관리 목록에서 해당 `Room`을 가리키는 `shared_ptr`이 삭제되면 어캄?

`AddClient()` / `RemoveClient()` 둘 다 `Manager` 객체의 `Room` 관리 목록을 통해서 호출되는데?(정책 1번 참조)

내가 지금 생각한건 이거임..

1. **소멸자**에서 `Manager`의 관리 목록(`rooms`)에서 해당 객체의 `shared_ptr`를 뺀다.
2. `Manager`를 통한 작업도 결국 소멸자가 호출되기 전에 실행될 수 밖에 없으니(`std::shared_ptr`를 들고있으므로)..

아 잠만 이거 안된다.

소멸자에서 해당 객체를 가리키는 `shared_ptr`를 해제하는건 영원히 해당 객체가 소멸되지 않는다.

이거 클로드랑 이야기해보다가 클로드가 아이디어 던져줌.

1. `members_mutex`의 의미를 해당 `Room` 객체의 상태를 바꾼다는 의미의 `room_state_mutex`로 재정의
2. 일단 `Manager::DeleteRoom()` 함수에서 해당 함수가 끝날 때 까지는 해당 `Room` 객체가 소멸되지 않도록 임시 `shared_ptr` 생성
3. `rooms.erase()` 해도 임시 `shared_ptr` 덕분에 해당 `Room` 객체는 살아있음
4. `Shutdown()` 함수까지 만들어서 해당 함수가 실행되지 않으면(누가 룸의 상태를 변경 중이면) 해당 `Manager::DeleteRoom()` 함수가 끝나지 않게 해서
    - `Shutdown()` 함수는 `room_state_mutex`를 잡은 후 `shutting.store(true)`를 수행한 후 `members`에 접근해 각 클라이언트의 `current_room`을 무효화함
5. 그렇게 하면,
    - 이미 `AddMember()`의 `shutting` 플래그 확인까지 지나버린 경우, `AddMember()` 함수는 `rooms_state_mutex`를 잡고있을 것이므로
    `Shutdown()` 함수가 호출되지 않고 임시 `shared_ptr`도 소멸되지 않아서 해당 `Room` 객체는 살아있게됨
    - `AddMember()`의 `shutting` 플래그를 확인하려면 `room_state_mutex`를 잡고있어야하므로 `shutting` 플래그 확인 전에 `Shutdown()` 함수가 제대로 호출된 경우에도 `shutting`을 보고 바로 중지됨

Ex. 물론 `JoinRoom()` / `LeaveRoom()` 함수에도 임시 `shared_ptr`를 사용해서 `Room` 객체를 살려놓음으로써 확실하게 `shutting` 플래그를 확인하고,
`JoinRoom()` / `LeaveRoom()` 함수 호출과 `AddMember()` / `RemoveMember()` 함수 호출(`room_state_mutex` 획득) 사이에 `Room` 객체가 날아가는 문제도 막음.

이 논리임.
결국 `DeleteRoom()` 할 때 이 구조를 적용해주면 됨.

```text
일단 shared_ptr로 해당 룸을 살려놓음

그 후에 rooms.erase()를 호출해도 임시 shared_ptr로 해당 룸이 살아있음

Room::Shutdown()을 호출해서 해당 룸의 상태를 변경하고 있는(AddMembers() / RemoveMembers() 등) 스레드가 없다면 shutting = true 수행,
해당 룸의 상태를 변경하고 있는 스레드가 있다면 여기서 blocking. 그렇다면 해당 함수가 종료되지 않아서 shared_ptr가 살아있게 됨.
    
그 후(Shutdown() 후)에 해당 룸의 상태를 변경하려고 하는 스레드가 있더라도 shutting == true 가드에 막혀 실패.
그리고 Shutdown() 후에 해당 룸의 상태를 변경하려고 하는 스레드는 room_state_mutex로 인해서 변경된 shutting을 볼 수밖에 없음.
```

1. 탐색 가능성(discoverability) — Manager::rooms 맵에 엔트리가 있는가 (rooms_mutex가 지킴)
2. 논리적 폐쇄(shutting) — 이 Room이 변경 작업을 받아줄 수 있는 상태인가 (Room::room_state_mutex가 지킴)
3. 물리적 생존(refcount) — shared_ptr 참조 카운트 (지난 대화에서 다룸)

> 문제가, 해당 룸의 상태를 바꾸는 연산 중에 `DeleteRoom()`에서 해당 룸의 마지막 `shared_ptr`이 사라져서 물리적으로 소멸되면 어째야하는지였는데
> 결국, `DeleteRoom()` 함수가 끝나야만 해당 `Room` 객체가 물리적으로 삭제되도록 임시 `shared_ptr`로 해당 룸 객체를 받아놓고
> 해당 룸의 상태를 바꿀 때 사용하는 뮤텍스(`Room::room_state_mutex`)를 `DeleteRoom()`(`Shutdown()` = `room_state_mutex` 잡음 / `shutting = true` / 모든 클라이언트의 참조 해제) / 다른 해당 룸의 상태를 바꾸는 연산이 잡게 해서
> 다른 해당 룸의 상태를 바꾸는 연산이 실행 중에는 `DeleteRoom()` 함수가 실행될 수 없게 해서
> 해당 룸의 상태를 바꾸는 연산 중에 해당 `Room` 객체가 소멸되지 않게 함.
> 그리고, 해당 룸의 상태를 바꾸는 연산에서 `room_state_mutex`를 잡은 후에 `shutting == true`를 확인하게 해서 `shutting = true`로 바꾸는 연산과 `shutting == true` 확인이
> 같은 `room_state_mutex` 안에서 일어나도록 해서 나중에 해당 룸에 대한 연산을 하려는 클라이언트도 `shutting == true`를 확인 후 작업을 수행하지 않음.

아, 그리고 룸 브로드캐스트는 이 문제에 영향받지 않음.
애초에 `ClientSession::current_room`을 사용해서 `shared_ptr`로 접근하기 때문에..
수명 문제가 발생하지 않음..

### 5-4. Lock Ordering과 데드락 예방(해결됨)

`Manager`의 룸 관련 함수들은 무조건 `Manager::rooms_mutex`랑 `Room::room_state_mutex`를 연속적으로 잡게됨.

하지만, 락을 중복해서 `A -> B` 순서로 잡는 함수와 `B -> A` 순서로 잡는 함수가 있으면 데드락이 발생할 위험이 매우 큼.

그래서 무조건 한 순서로만 락을 잡는 Lock Ordering이 필요함.

그래서,
무조건 `Manager::rooms_mutex`를 먼저 잡고 `Room::rooms_state_mutex`를 나중에 잡게 `Manager`의 함수들을 설계함.
(5-3의 부자연스러운 `shared_ptr`도 해당 룸을 살려놓는 구조도 `Manager::rooms_mutex`를 먼저 잡고 `erase()` 함수를 호출하기 위한 구조임.)

> 여러 락을 잡는 함수는 락을 잡는 순서가 일정하지 않으면 데드락이 발생할 수 있는데,
> 무조건 **중복해서 여러 락을 잡을 경우에는** `Manager::rooms_mutex` -> `Room::room_state_mutex` 순서로 락을 잡게 해서 데드락을 예방한다.
> 추가 : `ClientSession::current_room_mutex`도 추가됨에 따라 `Manager::rooms_mutex` -> `Room::room_state_mutex` -> `ClientSession::current_room_mutex` 순으로 잡게 한다.

### 5-5. `ClientSession`이 종료해야하는데 `Room`에 소속되어있는 경우(해결됨)

이 경우도 따져봐야지.

클라이언트가 갑자기 연결이 끊어진 경우같은거..

그리고 `Room`에 소속된 채로 연결을 끊은 경우.
이건 따로 해결해줘야함.

(5-1의 `ClientSession::current_room`과 `Room::members`가 동기화되어있다는 가정 하에 성립됨)

클라이언트의 `TryMarkClosing()` 종료 절차 진행 함수에서 진행하자.
결국 클라이언트가 어떤 이유로든 종료될 경우 해당 함수가 호출되게 되어있음.
무조건 해당 함수를 통과해야한다는말이지.

물론 해당 시점에 클라이언트가 룸에 소속되지 않았을 수도 있을테니까,
이렇게 진행하자.

```cpp
// TryMarkClosing() 함수 안

if (!current_room.expired()) {
    if (auto manager_sp = Manager_wp.lock()) {
        manager_sp->LeaveRoom(shared_from_this()); // LeaveRoom() 함수 도중에 룸이 폭파되어서 false가 반환된 경우도 상관 없음(애초에 이 코드는 룸이 폭파된 경우(current_room == nullptr) 실행되지 않아도 됨)
    }
}

// 기타 종료 코드
RemoveThisClient(); // 이건 꼭 룸 탈퇴 절차 후에 실행해야함. 이유는 생각안남.
```

이거 어차피 종료 절차라서 `current_room`에 대한 동기화를 수행할 필요는 없음.
(아닌가? 룸 변경 도중에 종료 절차를 수행한다면..)
(시발 날 그만 좀 괴롭히라고..)
(애초에 `current_room_mutex`가 읽기 / 쓰기 다 같이 쓰는 락이니까..)
(아닌가? 저 바로 위 코드의 주석이 그 문제를 해결한건가?)

아니다.
결국 저건(위의 주석은) 룸이 폭파되는 경우만 해당되지 저 타이밍에 룸을 나가는 연산이 실행되면..
잘 모르겠다.

어쨌든 저 종료 절차를 할 때도 `weak_ptr` 획득의 원자성은 보장해줘야하는게 아닌가 싶다.
하지만, 5-4에서 설명한 lock ordering 때문에 `current_room_mutex`를 잡은 상태로 `LeaveRoom()` 함수를 호출하면 안된다.
그렇기 때문에,
`current_room` `weak_ptr` 사용의 원자성만 보장해주는 형태로

- 해당 `weak_ptr`가 중간에 변경될 수 없도록 `weak_ptr`를 복사하는데만 락을 잡고 복사한 후
그 후에는 락을 놓고 복사한 `weak_ptr`로 `LeaveRoom()` 함수를 실행한다.
- 그 후 해당 `weak_ptr`이 변경된다고 해도, 어차피 종료될 세션으로 해당 `weak_ptr`도 어차피 사라질거라 상관없다.
- 그 전에 해당 `weak_ptr`가 `nullptr`로 변경되었다고 해도, 복사한 `weak_ptr`에 대한 `expired()` 검사에 막힌다.
- 도중에 해당 `weak_ptr`가 `nullptr`로 변경된다고 해도, 복사한 `weak_ptr`이기 때문에 문제가 없고,
어차피 종료될 세션이기 때문에 `weak_ptr`가 `nullptr`로 변경된 상태에서 종료되더라도 상관이 없다.
  - `current_room`이 `nullptr`로 변경되는 경우는 오직 `LeaveRoom()` 함수가 호출되었을 때 뿐이고,
  `LeaveRoom()` 함수가 호출하는 `RemoveMember()` 함수는 `room_state_mutex`로 `current_room`의 무효화 및 `Room::members`에서의 삭제를 `room_state_mutex`를 통해
  `Shutdown()`이 도중에 수행될 수 없도록 원자적으로 수행하기 때문에,
  `current_room`이 `nullptr`가 되어버렸다고 하면 `Room::members`에서도 해당 `ClientSession`이 제거되었다는게 보장이 되므로
  `RemoveMember()` 함수의 `find()` 함수로 인한 해당 `ClientSession`의 `Room::members` 컨테이너의 검사에 이미 `nullptr`로 바뀌었다는게 걸리게 된다.

이렇게 되기 때문에
`weak_ptr` 복사만 락을 잡고 수행한 후 그 후에는 락을 푼다.

그리고 그 사이에 다른 곳에서 `LeaveRoom()` 함수가 실행된 경우에도
해당 `LeaveRoom()` 호출도 `room_state_mutex`를 잡고 일어나기 때문에 또 `LeaveRoom()`이 호출된다면
이미 호출된 `LeaveRoom()`으로 `Room::members` / `ClientSession::current_room`이 다 없어질거라서
이후에 해당 종료 절차에서 `LeaveRoom()` 함수가 호출되었다면 `LeaveRoom()` -> `RemoveMember()` 함수 내부의 `find(client)` 결과값이 `end()` 이터레이터가 나와서
그 후의 `if`문에서 이중 종료가 걸러진다.

(물론 중간에 룸이 터지는 것도 `room_state_mutex`를 잡고 룸을 터트리기 때문에(`Shutdown()` 함수 구현과 5-3 참조)
`room_state_mutex`를 잡고 `shutting == true`를 확인하는 `if`문에 가로막혀서
중간에 룸이 터져도 상관 없다.)

변경된 코드는 이 정도라고 할 수 있겠다.

```cpp
// TryMarkClosing() 함수 안

std::weak_ptr<Room> current_room_for_termination;
{
    std::lock_guard<std::mutex> lock(current_room_mutex);

    current_room_for_termination= current_room;
}
// current_room 복사만 하고 락을 풀고나옴(lock ordering 지켜야함)
// 하지만, 종료 예정인 ClientSession의 current_room에 대한 원자성은 지켜야함.

// current_room_mutex를 들지 않고 복사한 weak_ptr로 종료 절차 수행
if (!current_room_for_termination.expired()) {
    if (auto manager_sp = Manager_wp.lock()) {
        manager_sp->LeaveRoom(shared_from_this()); // 어차피 이 작업은 room_state_mutex를 잡아야 실행되기 때문에 사전에 해당 함수(LeaveRoom())가 호출되었을 경우에도 문제 없음.
    }
}

// 기타 종료 코드
RemoveThisClient(); // 이건 꼭 룸 탈퇴 절차 후에 실행해야함. 이유는 생각안남.
```

> `ClientSession`이 종료해야하는데 `Room`에 소속된 경우,
> 종료 시 무조건 실행되는 `TryMarkClosing()` 함수에서 현재 룸에 소속되어있는지 확인한 후
> 별도로 룸에서 퇴장하는 `Manager::LeaveRoom()` 함수를 호출한다.

### 5-6. `Room::members`에 멤버를 넣고 빼는 연산이 굳이 `Manager`를 통해야할까?(취소된 아이디어)

이건 정책의 수정이 필요함.
1, 2번 정책의.
이유는 내일의 내가 알겠지.

솔직히 `Manager::rooms_mutex`는 `Manager::rooms`의 변경 / 읽기를 보호하기 위한 뮤텍스임.
근데 솔직히 그 룸 중 하나의 멤버를 바꾸는건.. 굳이 `rooms_mutex`를 잡을 필요가 있을까 싶음..

너무 무거울 듯. 그런 것까지 전체 뮤텍스를 잡으면..

그래서

- `AddMember()` : `Manager::JoinRoom()`
- `RemoveMember()` : `Manager::LeaveRoom()`

이 두 함수는 `ClientSession`에서 `Manager`를 통하지 않고 `ClientSession::current_room` 바로 호출하는게 좋을 듯.

- 어차피 이미 룸이 터져있으면 `current_room` `weak_ptr`에 `lock()` 함수를 실행했을 때 걸러낼 수 있을테고(애초에 룸이 터질 때 해당 `weak_ptr`를 무효화함)
- 중간에 `Shutdown()`되는 경우에도 **5-3**에 말한 것처럼 `Room::room_state_mutex`를 이용해서 애초에 중간에 `Shutdown()`되는 경우가 없게 구조가 짜여있고
- 이미 `JoinRoom()` / `LeaveRoom()`에서 임시 `shared_ptr`를 쓰는 이유인 객체 수명 보장도 `weak_ptr`로 `shared_ptr`을 얻어 접근하기에 문제 없고

그냥 `ClientSession`에서 `Manager`를 통하지 않고 `ClientSession::current_room`으로 바로 `Room::AddMember()` / `Room::RemoveMember()` 바로 호출하는게 좋을 듯.

계속 이거 마음에 걸렸음.
쓸데없이 `Manager::rooms`를 바꾸는 것도 아닌데 `Manager::rooms_mutex`를 잡고있는게 마음에 걸렸음.

아 아니구나. `JoinRoom()` 할 때는 `ClientSession::current_room`이 `nullptr`일테니,
결국 룸 목록(`rooms`)을 들고있는 `Manager`를 거쳐야 하고,
추상화 수준을 동등하게 맞추기 위해서 `rooms`를 거칠 필요가 없는 `LeaveRoom()`도 `Manager`를 통해서 해야겠구나.
(비슷한 유형의 기능을 제공하는 함수를 다른 객체에서 제공하면 헷갈릴 수 있을테니..)

이 아이디어는 취소!

### 5-7. 패킷 핸들러(`HandleRecvPacket()`)의 각 처리 과정도 각각의 함수로 분리하자.(실제 코드에 적용 끝남)

클라이언트든 서버든 간에
룸 시스템이 추가되면, 무조건 `HandleRecvPacket()` 함수의 크기가 너무 커질 것 같음..

그래서 `HandleRecvPacket()`의 각 처리 과정은 별개의 함수로 분리해야할 것 같음.

코드 간소화 말고도 장점은 있는데,
추후 `std::function` 객체에 패킷 처리 함수를 담을 때,
그 때 귀찮게 분리할 필요가 없어짐.
미리 분리해놓으면..

> 이건 앞으로의 정책임. 패킷 핸들러의 각 처리 과정은 별도의 함수로 분리.

### 5-8. `CreateRoom()` 함수에서 방을 중간에 생성하지 못했다면 어떻게 해야할까?(결론남)

> 즉, `CreateRoom()` 도중에 해당 `Room` 객체를 삭제해야하는 상황이 나오면 어쩔까?
> 대표적인게 `SetInitMember()` 함수의 실패다.
> 초기 멤버 설정을 실패했으므로 해당 방이 생성되면 안된다.
> 하지만 `CreateRoom()` 함수 도중이기 때문에, 어렵다..

이거 이미 해결 되어있었음.

`SetInitMember()` 함수가 실패했을 경우,

- `Manager::rooms`에 등록하는 코드를 실행하기 전에 `return`해서 
해당 `Room`객체는 `shared_ptr`로 관리되기 때문에 함수 끝나면 자동 소멸
- 그리고 결국 `SetInitMember()` 함수가 실패할 수 있는 경우가 애초에 해당 `ClientSession`이 잘못된 `ClientSession`이거나 `shutting == true`를 확인하는 것 밖에 없고,
  - `SetInitMember()` 함수 내부에서도 잘못된 `ClientSession`을 확인하고나서 `Room::room_state_mutex`를 잡은 채 `shutting == true`를 확인한 후 
  `ClientSession`에 `SetRoom()`을 수행하니까 문제가 없지.
  - 나중에 다른 `SetInitMember()` 함수를 종료하게 할 수 있는 조건이 나와도 `SetRoom()` 전에 확인하게 하면됨.

## 6. 예외 상황 목록(중요한 것들)

1. 입장 도중 Room 삭제(`room_state_mutex`를 사용해서 입장 도중에는 `Room`이 삭제될 수 없도록 보호(5-3 참조))
```text
Room 확인
→ Room 삭제
→ 죽은 Room에 Client 추가 시도
```

2. 마지막 멤버 퇴장과 새 Client 입장이 동시 발생(아마 마지막 멤버라고 판단하고 `Room` 삭제 후 새 Client에게는 오류로 처리할 예정)
```text
A: 마지막 멤버라고 판단하고 Room 삭제
B: 같은 Room에 입장 진행
```

3. Client 연결 종료와 입퇴장 처리 중복
```text
Join/Leave 처리 중
→ recv/send 오류
→ RemoveClient와 Room 정리가 동시에 실행
```

4. Client와 Room의 양방향 상태 불일치(`rooms_state_mutex`로 두 변경을 원자적으로 보호)
```text
Client는 Room A라고 함
Room A에는 Client가 없음
```

5. 방 이동의 절반만 성공(방 이동을 현재는 구현하지 않았음)
```text
기존 Room 탈퇴 성공
새 Room 입장 실패
```

6. Room.members 순회 중 멤버 변경(해결 -> snapshot으로 해결, GetMembers() 함수 참조)
```text
Broadcast 순회
→ 동시에 erase/insert
→ iterator 무효화 또는 대상 불일치
```

7. 여러 락을 획득하면서 데드락(lock ordering을 적용, 5-4 참조)
```text
Manager → Room
Room → Manager
```

8. Room 삭제 후 남아 있는 참조 사용(`Manager`에서 삭제된 `Room`에 접근할 때 `weak_ptr` 사용 / `find()` 검사로 해결)
```text
Manager에서 Room 삭제
→ Client나 작업 스레드가 과거 참조 사용
```
