## 룸 시스템 설계 개편안

이 문서는 [26.08.02 룸 시스템 설계](./26.08.02%20룸%20시스템%20설계.md) 문서를 읽었다는 가정 하에 작성됨.

> 다음에 할 것 : 로그 작성 코드 작성하기.
> 다다음에 할 것 : 서버 쪽 패킷 핸들러에 룸에 대한 연산 설정하기.

> 안 한 것들 : `Manager::CreateRoom()` 함수 / 패킷 핸들러 / 패킷 프로토콜 / 클라이언트 입력 파싱

기존 룸 시스템 설계안에서는 여러 스레드가 동시에 룸에 대한 수정을 진행했기 때문에
논리적으로 다양한 상황이 동시에 벌어질 수 있어서
예외처리 난이도 및 데드락 방지 난이도가 정말로 어려워졌었음..

```text

  Thread A ─┐
  Thread B ─┼─→ Room::members 동시 접근
  Thread C ─┘         ↑
              room_state_mutex, shutting CAS,
              shared_ptr 임시 연장, lock ordering...
              → "동시에 여러 명이 같은 상태를 바꿀 수 있다"는
                전제 때문에 생긴 방어 코드 전부

                좆 같 다 !
```

이 개편안은 기존 룸 시스템처럼 여러 스레드가 동시에 룸에 대한 수정을 진행하지 않고,
해당 룸의 별도 워커 스레드만이 해당 룸을 수정할 수 있도록 하고,
`std::mutex` / `std::condition_variable` / `std::queue`를 이용한 `Message Queue` 구조와 `Command` 패턴으로
기존 룸 시스템을 개편함.

기존의 단점은 한 룸의 상태 변경을 여러 스레드가 진행해서 상태가 엉킬 수 있고 동기화 및 데드락 처리가 어려울 수 있다는 것이었음.
그래서 오직 한 스레드에서만 해당 룸의 상태 변경을 해서 그 문제를 해결하는 구조가 `Message Queue` 구조와 `Command` 패턴임.

결국, 해당 룸에 대한 상태 변경 요청과
실제 실행 사이의 락 중첩을 막기 위해서
이런 구조를 선택했다고 보면 됨.

> Room의 상태를 바꾸는 주체를 하나로 만든다.

이게 이 설계 변경을 설명하는 한 줄임.

`RoomTask`는 `Command`패턴을 적용하고,
`Room`에 대한 "이벤트"는 전부 `RoomTask`로 놓는다.

- JoinRoomTask
- LeaveRoomTask
- BroadcastRoomTask
- ShutdownRoomTask

```text
  Thread A ─┐
  Thread B ─┼─→ [ Room의 메시지 큐 ] → Room 전용 처리 루프(1개)가 순차 처리
  Thread C ─┘         (mutex는 큐 하나만 보호)
  
  Join / Leave / Shutdown / broadcast
      전부 "메시지"로 큐에 넣고 끝.
      실제 members / shutting 변경은 큐를 꺼내는 쪽에서 혼자만 함.
```

## 0. 중요한 내용(기존 룸 시스템 설계 문서에서 복붙)

룸 시스템의 송 / 수신 로직은
기존 `ClientManager` 기반 브로드캐스트에서 `Room` 기반 브로드캐스트로
**송신되는 범위만 달라진다.**

하지만,

- 메시지를 서버가 송 / 수신하는 도중에 룸이 폭파된다거나
- 입장하는 도중에 룸이 폭파된다거나
- 여러 클라이언트 세션이 동시에 입장한다거나
- 룸에 들어가려하는데 이미 룸이 폭파되어있다거나

하는 예외 처리가 대부분일 것 같다.. 힘들겠다..

여기서 중요한거!

`Room`의 물리적 소멸과 논리적 폐쇄, Message Queue의 논리적 폐쇄는 다르다.

- 물리적 소멸 : `shared_ptr`에 의해서 일어남(어떤 `shared_ptr`도 해당 `Room`을 참조하지 않음)
- 논리적 폐쇄 : `shutting`에 의해서 일어남(`shutting == true`라면 해당 룸은 더이상 사용되면 안됨, 하지만 물리적으로 소멸됐다는건 아님)
- 논리적 Message Queue 폐쇄 : `ShutdownRoomTask`에 의해서 일어남(`ShutdownRoomTask`가 해당 큐에 Push되면 더이상 어떤 다른 `RoomTask`도 Push되지 않음)

결국 이제 서버의 로직은 두 계층으로 분리된다.

- 송수신 로직 : Send / Recv Thread 관련
- 이벤트 로직 : 닉네임 시스템 / 룸 시스템 등

이 두 가지를 분리해서 생각해보자.

### 0-1. 불변식들

> 안지키면 큰일나는 사실들.

1. Manager에 없는 Client는 어떤 Room에도 없어야 한다.
2. Manager에 없는 Room을 Client가 참조하면 안 된다.
3. Client가 Room을 참조한다면 Room.members에도 Client가 있어야 한다.
4. Room.members에 Client가 있다면 Client도 그 Room을 참조해야 한다.
5. 한 Client는 최대 한 Room에만 존재해야 한다.
6. 삭제된 Client나 Room에는 이후 어떤 작업도 수행되면 안 된다.
7. 논리적 폐쇄된 Room에는 이후 어떤 새로운 작업도 수행되면 안 된다.

```text
client.current_room == room
    ⇔
room.members contains client
```

이게 중요.

### 0-2. 구현 단계

1. **불변식과 정책을 지키며** 예외를 무시한 채 필요한 기능만 구현
2. 예외 처리(예외 상황 목록 참조)
3. 룸 시스템을 완성한다면 `Echo Server.cpp`을
`Echo Server.cpp` / `Room.h` / `Room.cpp` / `ClientSession.h` / `ClientSession.cpp` / `Manager.h` / `Manager.cpp`로 분리(클로드 코드에게 해달라고 할 예정)

### 0-3. 과거 설계에서의 정책

> 불변식과 별개로, 설계 도중에 한계 등으로 생긴 지켜야하는 사실들.. 이었던 것. 현재 설계에서는 사용하지 않음

1. `Manager::rooms`의 상태를 바꾸거나 해당 목록을 사용해야하는 동작(5-6 참조)은 `Manager`를 통한다. (예 : 룸 생성 / 룸 삭제 / 입장 / 퇴장(이건 추상화 수준 맞추기 용))
2. 해당 룸의 상태를 바꾸지 않는 동작은 `Manager`를 통하지 않고 `Room`에서만 처리해도 된다.(예 : 브로드캐스트 등)
3. `shutting`을 바꾸는 동작은 1번 정책에서 예외이다.(`shutting`을 바꾸는 동작은 `Manager`를 통하든 안통하든 상관없다. 급한거니까.)(추가 : `shutting`은 `Room::Shutdown()` 함수에서만 일어난다. 그러므로 이 정책은 어느정도는 무효이다.)
4. 락을 잡는 순서는 무조건 `Manager::rooms_mutex` -> `Room::room_state_mutex` -> `ClientSession::current_room_mutex` 순서로 잡아 데드락을 사전에 예방한다.
5. 룸의 특정 `ClientSession`을 `Join` / `Leave`하는 권한은 오직 해당 `ClientSession`만 가진다.(아직 강퇴 기능 / 타인에 의한 퇴장 기능 없다는 이야기)
6. 룸 브로드캐스트 시, 이미 `shutting == true`가 되었다고 해도 해당 브로드캐스트는 전부 수행하고 해당 룸 브로드캐스트 함수를 종료한다.(계속 `shutting == true`를 검사하는 branch prediction 비용을 줄이기 위함)
7. `Room`에 대한 모든 상태 변경은(폐쇄 절차 포함) `Room::room_state_mutex` 안에서 배타적으로 일어난다.(5-1, 5-2, 5-3 등 많은 부분에 영향을 끼침.)

### 0-4. 현재 설계에서의 정책

#### 서버 내부 이벤트 관련

1. 해당 룸의 모든 이벤트는 `Room::tasks`에 실행할 작업을 담는 식으로 실행한다.
2. 하지만 해당 `Room::tasks`에 작업을 넣는 방법은 굳이 `Manager`를 통하지 않아도 된다.
3. 각각의 룸을 담당하는 스레드는 각각의 룸이 종료될 때 `join()`으로 끝을 책임진다.
4. 룸에 대해 수행되는 작업들에 대해서 룸을 담당하는 스레드와 룸 객체의 생성자 / 소멸자로 로그를 찍는다.
5. `Manager`에서 해당 룸에 넣을 `RoomTask`를 생성하고, `Room`에서는 그저 해당 `RoomTask`를 기반으로 실행만 한다.
6. 만약 `Room::tasks`에 `ShutdownRoomTask` 객체가 들어간 경우, 별도의 플래그를 세팅하고 더이상 해당 Message Queue에 대한 어떤 push()도 허용하지 않는다.
7. `Manager::LeaveRoom()`(`future.wait()` 포함)은 `Room Worker Thread`에서 호출하면 안 된다.

#### 네트워크 송 / 수신 관련

1. 정책 수정 : 페이로드에 아무 것도 안 보내는 것은 일부 패킷 타입에서는 정상적인 동작으로 처리한다.
   - 일부 패킷 타입 : 페이로드에 어떤 내용도 필요 없는 패킷 타입들
   - 그리고 이에 맞춰 송 / 수신 함수를 개편한다.
   - 개편안 : 헤더를 정상적으로 수신하고
   -> 헤더에 명시된 페이로드의 길이가 0이면
   -> 페이로드를 수신하지 않고 페이로드를 빈 문자열로 맞춘 채 그 자리에서 반환
   (송신할 때도 마찬가지)
   - 헤더를 정상적으로 수신하고
   -> 헤더에 명시된 페이로드의 길이가 0이면
   -> 페이로드를 송신하지 않고 그 자리에서 반환

#### Lock Ordering

```text
rooms_mutex -> tasks_mutex -> current_room_mutex

주의 : 한 단계를 건너뛰고는 락을 잡아도 되지만, 절대 !역순!으로는 락을 잡으면 안됨.
```

### 0-5. 현재 구현 안하는 기능들

1. 룸 이동 기능
2. 룸 인원 / 모든 룸 정보 등 룸의 정보를 제공하는 기능

### 0-6. 현재 구현 해봄직한 기능들

1. 룸에 인원이 더이상 안 남아 있는 경우 해당 룸을 삭제하는 기능(마지막 나가는 스레드가 해당 룸을 삭제, `shared_ptr`처럼)

## 1. 기본적인 구조

```text
             Manager
      ┌──────────────────┐
      │ Client 목록      │
      │ Room 목록        │
      └──────┬───────────┘
        shared_ptr 로 소유
     ┌───────┴────────────────────────────┐
     │                                    |
     ↓                                    ↓
 ClientSession                          Room
 ClientSession    weak_ptr로 상호 참조   Room
 ClientSession                          Room
```

```text
             여러 ClientSession / Manager
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       JoinTask   BroadcastTask   LeaveTask
          │            │            │
          └────────────┼────────────┘
                       ↓
                [ Room Task Queue ]
                       │
                 mutex + CV
                       │
                       ↓
                  Room Worker
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
       members     shutting      기타 Room 상태
```

### 1-1. Manager

(현 ClientManager)

- 모든 ClientSession 관리
- 모든 Room 관리
- Room 생성
- Room 삭제(메시지 큐)
- Client를 Room에 넣고 빼기(메시지 큐)
- 전체 브로드캐스트(이미 구현되어있는 기능임 이건)

이 객체에서 룸의 상태를 바꾸는 동작이 일어난다.

#### 필요한 동작

- Room 생성
- Room 삭제(메시지 큐)
- Room에 클라이언트 입장(메시지 큐)
- Room에서 클라이언트 퇴장(메시지 큐)
- 룸 브로드캐스트는 룸의 상태를 바꾸지 않으므로 없음

### 1-2. Room

- 자기 방에 속한 Client 목록만 관리
- Room 내부 브로드캐스트

이 객체에서 해당 룸의 상태를 바꾸지 않는 동작들이 일어난다.

#### 필요한 동작

- 해당 Room에 특정 멤버 추가
- 해당 Room의 특정 멤버 삭제
- 해당 Room 폐쇄 처리(`shutting.store(true)`)
- 해당 Room에 브로드캐스트

해당 Room에 특정 멤버 추가 / 삭제, 해당 Room 폐쇄 등의 룸의 상태를 바꾸는 동작은 `Manager`의 함수들을 통해서 일어남.
해당 Room에 브로드캐스트 하는 부분은 `ClientSession`의 `current_room` `weak_ptr`를 사용해서 일어남.

### 1-3. ClientSession

- Manager 참조
- 자신이 속한 Room 참조(현재는 단일 룸 구조로 할 생각)

여기서 해당 클라이언트에 대한 실질적 송 / 수신 및 기본적인 패킷 처리가 일어난다.

## 2. 아이디어들과 문제들

## 2-1. 메시지 큐의 기본적인 아이디어

메시지 큐란, 실행할 작업들을 담는 큐다.
별도의 Room 별 Worker 스레드가 해당 큐에서 작업들을 하나씩 꺼내 실행한다.

그래서 해당 Message Queue의 상태를 바꾸는 것에 대한 `std::mutex`가 필요하다.

`Manager`의 함수들도 새 룸을 생성하는 `CreateRoom()` 함수를 제외하고는
모든 작업을 해당 룸의 메시지 큐(`tasks`)에 `RoomTask`를 넣는 것으로 수행한다.

그리고 룸을 생성할 시, 해당 룸의 작업을 처리하는 별도의 스레드도 생성해야한다.
그 스레드는 해당 룸 폐쇄 시 `join()`으로 종료를 확인한다.(`detach()` 때문에 해당 스레드의 종료를 알 수 없지 않게 하기 위함)

메시지 큐에는 해당 룸에서 실행할 이벤트를 나타내는 `RoomTask`를 담는다.
물론 `RoomTask`에는 `Command` 패턴을 적용한다.

### Manager에 대한 개편 내역

```cpp
class Manager : public std::enable_shared_from_this {
private:
    // ...
    std::unordered_map<RoomID, std::shared_ptr<Room>> rooms;
    std::unordered_map<RoomID, std::thread> rooms_threads; // 룸들의 스레드를 보관해놓은 컨테이너
    std::mutex rooms_mutex; // 읽기 / 쓰기 락, unordered_map은 읽기와 쓰기가 같이 있으면 읽기가
    std::mutex rooms_threads_mutex;
    std::atomic<RoomID> current_room_id_to_be_generated;
public:
    Manager() : current_room_id_to_be_generated(0) {

    }

    bool CreateRoom(std::shared_ptr<ClientSession> client_to_create);
    bool DeleteRoom(RoomID room_id);

    bool JoinRoom(RoomID room_id, std::shared_ptr<ClientSession> client);
    bool LeaveRoom(std::shared_ptr<ClientSession> client);

    void RemoveRoomToManager(RoomID room_id);
};
```

#### CreateRoom()

> 1. 해당 룸의 id를 발급하고
> 2. 해당 룸 객체를 생성하고(id가 있어야함)
> 3. 해당 룸 객체를 `rooms`에 등록하고(룸 객체가 생성되야함)
> 4. 해당 룸 객체를 전담하는 스레드를 만들고
> 5. `Room::AddMember()`로 초기 멤버 설정까지 해주는 함수

호출 주체 : `ClientSession`

잡아야하는 락 : 룸 목록에 다른 스레드의 출입을 막을 때 `rooms_mutex` / 방을 생성한 첫 멤버를 룸에 추가할 때 `tasks`에 작업을 push() 하기 위해서 사용하는 `tasks_mutex`

중요한 점 : 이 함수는 처음으로 룸 객체를 생성하는 스레드이므로 전용 `RoomTask`를 가지고 있지 않지만,
첫 멤버(해당 룸을 생성한 클라이언트)는 `JoinRoomTask`로 처리함.

(할일 참 많다ㅋㅋ)

```cpp
bool Manager::CreateRoom(std::shared_ptr<ClientSession> client_to_create) {
    if (client_to_create == nullptr) {
        return false;
    }

    RoomID this_room_id = current_room_id_to_be_generated.fetch_add(1);
    std::shared_ptr<Room> this_room = std::make_shared<Room>(this_room_id, shared_from_this());

    std::thread assigned_thread(room_thread, this_room);

    auto task = std::make_shared<JoinRoomTask>(client_to_create);
    auto future = task.GetFuture();

    this_room.RoomTasksPush(task);

    if (!future.get()) {
        return false;
    }

    // 앞 구간에서 예외가 터지면 정상적인 룸이 아닐 것이기 떄문에 룸이 그대로 증발하도록 룸 목록에 추가를 마지막에 함
    {
        std::lock_guard<std::mutex> rooms_lock(rooms_mutex);
        rooms[this_room_id] = this_room;
    }

    {
        std::lock_guard<std::mutex> rooms_threads_lock(rooms_threads_mutex);
        rooms_threads[this_room_id] = std::move(assigned_thread);
    }

    return true;
}
```

#### DeleteRoom()

> 입력받은 room_id를 보고
> 해당 룸을 폐쇄하는 작업을 해당 룸의 `tasks` 큐에 넣는 함수

호출 주체 : `ClientSession`

잡아야하는 락 : 룸 목록에 다른 스레드의 출입을 막을 때 `rooms_mutex` / `tasks` 큐에 push() 할 때 사용하는 `tasks_mutex`

중요한 점 : 오직 `tasks`에 push() 하고 해당 스레드는 더이상 락을 잡지 않고 룸 스레드가 해당 작업을 비동기로 실행함.(`current_room_mutex` 까지 잡지 않음)
**이 중요한 점은 `Manager`의 다른 함수들도 포함(복붙 귀찮음)**

```cpp
bool Manager::DeleteRoom(RoomID room_id) {
    std::shared_ptr<Room> room;
    {
        std::lock_guard<std::mutex> lock(rooms_mutex);

        auto it = rooms.find(room_id);
        if (it == rooms.end()) {
            return false;
        }

        room = it->second;
    }

    auto task = std::make_shared<ShutdownRoomTask>();

    if (!room->RoomTasksPush(task)) {
        return false;
    }

    // 어차피 join()이 기다리는 함수니 Shutdown()이 종료될 때까지 기다릴 필요는 없음.
    // Room::shutdown()이 실행됐다면 shutting == true일 것이므로 해당 스레드는 종료됨
    std::thread this_room_thread;
    {
        std::lock_guard<std::mutex> lock(rooms_threads_mutex);

        auto it = rooms_threads.find(room_id);
        if (it == rooms_threads.end()) {
            return false;
        }
        
        this_room_thread = std::move(it->second);
        rooms_threads.erase(room_id);
    }

    // 오래 걸릴지도 모르는 무거운 join()은 lock을 잡지 않고 실행
    if (this_room_thread.joinable()) {
        this_room_thread.join();
    }

    return true;
}
```

#### RoomTasksPush()

> `tasks_mutex`를 잡고 해당 룸에 `RoomTask`를 `push()` 하는 함수

호출 주체 : `Manager`

해당 함수에서 잡아야하는 락 : `tasks` Message Queue에 `RoomTask`를 넣을 때 `task_mutex`

오직 이 함수로 해당 룸에 대한 상태 변경 요청을 함.

```cpp
bool Room::RoomTasksPush(std::shared_ptr<RoomTask> task_requested_by_client) {
    {
        std::lock_guard<std::mutex> lock(tasks_mutex);

        if (is_tasks_shutting) {
            return false;
        }
        if (dynamic_cast<ShutdownRoomTask*>(task_requested_by_client.get())) { // 다운캐스팅해서 입력받은 RoomTask가 ShutdownRoomTask인지 판별
            is_tasks_shutting = true;
        }

        tasks.push(task_requested_by_client);

    }

    tasks_and_shutting_cv.notify_one(); // 하나의 RoomTask가 push되었으니 잠들어있는 해당 룸의 스레드를 깨움

    return true;
}
```

여기서 왜 '대충 앞으로의 RoomTaskPush()가 무조건 false를 반환하게 하는 코드'라고 주석을 달아놨냐면,
(if문으로 `ShutdownRoomTask`를 확인하는 부분에서)
단순하게 `shutting` 플래그를 사용하면 `Room::RoomRun()` 함수가 `shutting` 플래그를 사용해 종료되어서
`ShutdownRoomTask` `push()` 타이밍 == `Room::RoomRun()` 함수 종료 타이밍이 되어서
아직 `Shutdown()` 함수는 호출되지도 않았는데 그 함수를 실행해야할 `RoomRun()` 함수가 종료되어버리는 불상사가 벌어질 수 있음.
그리고 아직 실행되지 않았던 작업들도 날아가버림.

그래서 오직 `tasks` 큐에만 `push()` 할 수 없게 하는 플래그가 필요했음.
그게 `is_tasks_shutting` 플래그임.

```text
  recv_thread                                  room_thread(RoomRun())
     |                                              |
     |                                              |
     |                                              | (wait())
     ↓                                              | 
ShutdownRoomTask                                    ↓
  push() 됨  ------> shutting = true ------>     if (shutting == true) break; 즉, room_thread 종료
                                                    |
                                                    | (shutting == true 후 작업 pop())
                                                    ↓
                                                아직 tasks에 남아있는 
                                                ShutdownRoomTask 이전 작업들은
                                                실행되지 못하고 종료됨
                                                물론, ShutdownRoomTask도 실행되지 못함 

그래서, shutting과 별도로 "더이상 해당 tasks Message Queue에는 push()되면 안된다는 것을 알려주는 포인터가 필요함.
```

#### RoomTasksPop()

> `tasks_mutex`를 잡고 `RoomTask`를 `pop()` 하는 함수
> 이 함수는 해당 룸을 담당하는 스레드가 호출해서
> 해당 룸에 대한 작업을 수행한다.

호출 주체 : 오직 `RoomRun()`

해당 함수에서 잡아야하는 락 : `tasks` Message Queue에서 `RoomTask`를 빼낼 때 `tasks_mutex`

```cpp
std::shared_ptr<RoomTask> Room::RoomTasksPop() {
    std::shared_ptr<RoomTask> result;
    {
        std::lock_guard<std::mutex> lock(tasks_mutex);
        result = tasks.front(); // tasks 큐의 맨 앞 작업 꺼내서 shared_ptr 복사
        tasks.pop();
    }

    return result;
}
```

#### AddMembers()

> 해당 룸에 새로운 클라이언트를 추가하는 함수

호출 주체 : 오직 `RoomRun()`

해당 함수에서 잡아야하는 락 : `current_room_mutex` / `members`에 대한 변경을 원자적으로 수행할 때 `ClientSession::current_room_mutex`

```cpp
bool Room::AddMember(std::shared_ptr<ClientSession> client) {
    if (!client || (client->GetRoom() != nullptr)) false;

    // 정책을 ShutdownRoomTask가 push() 된 후에는 새로운 작업을 큐에 넣지 않는 것으로 잡았으므로 shutting == true 검사는 필요 없음

    // 룸을 수정하는 주체가 스레드 하나이기에 룸에 상태에 대한 락은 필요 없음,
    // 하지만 클라이언트의 current_room을 수정하는 스레드는 여러개일 수 있기 때문에 current_room_mutex의 unique_lock을 얻음
    std::unique_lock<std::mutex> client_lock = client->GetCurrentRoomLock();
    client_lock.lock();
    
    // members가 변하면 -> current_room도 변하도록 미리 current_room_mutex를 잡아둠
    // 중간에 다른 스레드가 current_room을 변경할 수 없어 room.members contains client <-> client.current_room == room이 성립함
    client->SetRoomUnlocked(shared_from_this());
    members[client->GetSessionID()] = client;

    return true;
}
```

#### RemoveMembers()

> 해당 룸의 해당 클라이언트를 제거하는 함수

호출 주체 : 오직 `RoomRun()`

해당 함수에서 잡아야하는 락 : `current_room` / `members`에 대한 변경을 원자적으로 수정할 때 `ClientSession::current_room_mutex`

```cpp
bool Room::RemoveMember(SessionID session_id) {

    auto it = members.find(session_id);
    if (it == members.end()) return false;

    auto client_wp = it->second;

    if (auto client_sp = client_wp.lock()) {
        std::unique_lock<std::mutex> client_lock = client_sp->GetCurrentRoomLock();
        client_lock.lock(); // 위와 같은 이유로 current_room_mutex를 먼저 잡고 current_room / members에 대한 변경을 진행함

        client_sp->SetRoom(nullptr);
        members.erase(session_id);
    }


    return true;
}
```

#### RoomRun()

> 해당 룸을 담당하는 스레드가 실행할 함수
> `std::condition_variable`을 이용해서 `tasks` 큐에서 `pop()`을 한 후 해당 작업에 대한 처리를 한다.

해당 함수에서 잡아야하는 락 : 조건 변수의 조건을 확인할 때 `tasks_mutex`

```cpp
void Room::RoomRun() {
    while (true) {
        {
            std::unique_lock<std::mutex> lock(tasks_mutex);
            while (tasks.empty() && !shutting) { // 아직 큐가 비어있고 shutting == false라면 깨어나면 안됨
                tasks_and_shutting_cv.wait(lock);
            }
            
            // 만약 방금 실행(Execute())한 작업이 ShutdownRoomTask여도 while문 검사에서 !shutting으로 wait() 함수를 호출하지 않게 되고,
            // 해당 if문을 만나서 안전하게 break됨.
            // 더 이상 작업이 없게 되어서 영원히 대기하지 않음.
            if (shutting) {
                break;
            }
        }
        
        auto task = RoomTasksPop();

        task.Execute(*this);

    }
}
```

#### GetCurrentRoomLock()

> 해당 객체 외부에서 `current_room_mutex`가 필요할 때 사용할 함수
> 잠기지 않은 `std::unique_ptr`의 형태로 반환하며,
> 현재는 `ClientSession::current_room`과 `Room::members`의 원자성을 보장하기 위해 
> `Room`에서 해당 뮤텍스를 얻어서 `std::lock()` 함수를 호출해버리기 위해 사용.

호출 주체 : `Room::AddMember()` / `Room::RemoveMember()` 등 `ClientSession::current_room`과 `Room::members`의 동기화가 필요한 곳

> 고려할 것 : 굳이 `std::defer_lock`으로 잠근 상태로 해당 `std::unique_lock`을 반환할지 다시 생각해봐야함.

```cpp
std::unique_lock<std::mutex> ClientSession::GetCurrentRoomLock() {
    std::unique_lock<std::mutex> lock(current_room_mutex, std::defer_lock); // 잠그지 않고 전달하기 위해 std::defer_lock 옵션 사용
    return lock;
}
```

## 2-2. 작업(RoomTask)들에 대한 기본적인 아이디어

`Manager::CreateRoom()` 짜다가 문제가 발생함.

그냥 모든 `RoomTask`에 `promise`를 사용할까 싶기도 함.

모든 `RoomTask` 말고 결과 확인이 필요한 `RoomTask`에 `promise`를 사용하자.
이게 모든 `RoomTask`에 그렇게 처리를 하면 사실상 동기 처리와 다를 바가 없어짐..

그래서 불변식을 깰 수도 있어서 결과 확인이 꼭 필요한 `JoinRoomTask` / `LeaveRoomTask`에만 `promise`를 적용하는걸로.

### RoomTask

```cpp
class RoomTask {
public:
    virtual ~RoomTask() = default;
    virtual void Execute(Room& room) = 0;
};
```

#### JoinRoomTask

```cpp
class JoinRoomTask : public RoomTask {
private:
    std::shared_ptr<ClientSession> client;
    std::promise<bool> res;
public:
    JoinRoomTask(std::shared_ptr<ClientSession> _client) : client(_client) {
        
    }
    std::future<bool> GetFuture() {
        return res.get_future();
    }
    void Execute(Room& room) override {
        res.set_value(room.AddMember(client));
    }
};
```

#### LeaveRoomTask

```cpp
class LeaveRoomTask : public RoomTask {
private:
    SessionID session_id;
    std::promise<bool> res;
public:
    LeaveRoomTask(SessionID _session_id) : session_id(_session_id) {

    }
    std::future<bool> GetFuture() { // 작업이 끝났음을 나타내는 future를 get하는 getter 함수
        return res.get_future(); 
    }
    void Execute(Room& room) override {
        res.set_value(room.RemoveMember(session_id)); // 해당 작업이 실제로 처리되었다는 신호
    }
};
```

## 이유들

- 왜 기존 구조를 버렸나?
  - 여러 스레드가 동시에 해당 룸의 상태를 변경할 수 있는 구조여서 객체 생명주기 / 락 등이 너무 복잡해져서

- 왜 Message Queue?
  - 한 룸에 대한 작업을 처리하는 스레드를 하나의 스레드로 단일화하고,
  여러 스레드에서 동시에 해당 룸에 대한 작업을 수행하려고 할 때 오직 Message Queue 하나의 동기화만 신경쓰면되니까.

- 왜 Command 패턴 / RoomTask?
  - Command 패턴은 다양한 요소가 필요한 다양한 작업들을 하나의 객체에 담을 수 있게 해주어서 RoomTask라는 Command 패턴이 적용된 객체를 사용함

- 왜 Room마다 Worker 하나?
  - 왜 기존 구조를 버렸냐 / 왜 Message Queue를 사용하냐에서 이어짐.
  - 룸 마다 여러 워커 스레드가 해당 룸에 대한 연산을 실행하는건 기존 구조와 다를 뿐도 없을 뿐더러,
  그 점 때문에 추가적인 동기화가 필요해짐.

- Manager와 Room의 책임 분리 이유
  - Manager의 책임을 오직 해당 Room의 Message Queue에 push()로 한정하기 위해서.
  그리고 룸의 워커 스레드는 오직 해당 Room의 Message Queue에 들어온 RoomTask를 pop() 해서 처리하면 되기 때문에,
  룸에 대한 조작을 할 때 Room 내부의 문제가 Manager까지 전달되지 않음.
  - 이걸 비동기 처리라고 하나?
  - (적어보니까 Send Queue랑 비슷한 이유네.)

- CreateRoom은 왜 Queue 밖?
  - 이건 해당 룸 객체 자체를 생성하는 연산이기 때문에
  아직 Room 객체가 생성되지 않아서 존재하지 않는 Message Queue에다가 작업을 넣을 수 없기 때문.
  - 그래서 이것만 유일하게 Message Queue에서 pop() 하는 식으로 처리하지 않고, 별도로 처리함.
  - 그리고 해당 Message Queue에서 pop() 및 작업 수행을 하는 스레드를 생성하는 것 자체도 CreateRoom 함수가 해줘야 하는 일이기 때문에..
  - **물론 초기 멤버 삽입은 이미 Message Queue와 Worker Thread가 생성된 후에 제대로 tasks Message Queue를 통해 진행됨..**
    - (룸 생성과 별개의 작업이긴 하니..)

- DeleteRoom을 왜 바로 삭제하지 않고 ShutdownTask로?
  - 이러면 기존 Room 구조에서 발생했던 Room 상태 변경 중 해당 객체가 사라지거나 하는 문제가 재발함.
  - 즉, 동시에 해당 룸에 대한 상태 변경이 일어날 수 있게 된다는거임.
  - 그래서 DeleteRoom 자체도 하나의 해당 룸에 대한 이벤트로 취급해서 다뤄서
  다른 작업 도중에 종료 절차가 실행되는 문제를 막을 수 있음.
  - 물론 해당 룸에 대한 더 이상의 작업을 막기 위해 ShutdownTask가 tasks에 push되고 나서는 다른 RoomTask가 tasks에 들어올 수 없게 함.

- 왜 current_room_mutex를 std::recursive_mutex로?
  - 해당 뮤텍스를 두 번 잠가야 하는 부분이 Room::AddMember() / Room::RemoveMember() 함수에 필요했기 때문.
  - 왜 두 번 잠가야하는지에 대한 가장 큰 문제는 ClientSession::SetRoom() 인데,
  해당 함수 내부에서는 프로그래머가 실수할 것을 대비해 강제적으로 current_room_mutex를 잡게 함.
  - 그리고, current_room의 변경과 Room::members의 변경 사이에 다른 스레드에서 해당 current_room을 수정할 수 없도록,
  AddMember() / RemoveMember()에서는 current_room_mutex를 SetRoom() 함수와는 별개로 SetRoom() 전에 잡아놔야함.
  - 결국, SetRoom() 에서 current_room_mutex를 잡는 부분을 빼면 해결되는 문제지만,
  혹시 그거 뺀 이후에 SetRoom()을 호출할 때 current_room_mutex를 잡고 해당 작업을 수행하지 않을까봐 이렇게 함.
  - **이 문제는 다시 std::mutex로 바꾸며 Locked / UnLocked 버전 함수를 따로 만들어서 분리함.**

- 왜 `LeaveRoomTask` / `LeaveRoom()` 함수에는 `future` / `promise`를 사용해 `LeaveRoomTask.Execute()`, 즉 `RemoveMember()`의 실행을 알려줌?
  - `LeaveRoom()` 함수가 실행되었다고 해서 실제로 해당 룸에서 퇴장 처리가 진행된 것이 아니라 `LeaveRoomTask`가 `tasks` 큐에 넣어진 것 뿐임.
  - 하지만 해당 `LeaveRoom()` 함수를 호출했을 때 확실하게 `RemoveMember()`가 실행되었다는 증거가 필요함.
    - 왜 그렇냐면, `TryMarkClosing()` 등 `tasks` 큐에 `push()`가 아니라 아예 해당 `RemoveMember()` 작업 자체가 끝났다는 것을 보장할 필요가 있기 때문임.
      - `RemoveMember()`의 실행을 확인하지 않고 다음 과정인 `RemoveThisClient()`를 호출하게 된다면,
      1번 불변식, '`Manager`에 없는 `client`는 어떤 `room`에도 있으면 안된다'는 불변식이 깨짐.
  - **즉, `Manager::LeaveRoom()` 함수는 `Room::RemoveMember()` 함수의 실행을 기다릴 필요가 있기 때문에 `promise` / `future`로 해당 함수의 실행을 보장하는 것.**
  - `LeaveRoom()` 함수의 실행은 그저 `Room::tasks`에 `LeaveRoomTask`를 `push()`한 것일 뿐, `Room::RemoveMember()` 함수가 실행된 것은 아니었으므로..

- 왜 각 룸의 스레드를 룸과 분리해서 저장함?
  - 결국 `tasks` 큐를 통하지 않은 해당 룸 객체의 상태 변경을 수행하지 않기 위해서 이렇게 한거임.
  - 분리해서 저장하면, 해당 룸을 다루는 스레드를 매니저에서 바로 찾을 수도 있고,
  해당 룸 객체에 접근할 필요가 없어져서
  `Manager`에서 `join()`을 할 때도 해당 룸 객체의 상태에 접근하지 않아도 됨.
  - 그리고 해당 객체와 해당 스레드가 결합이 되어있으면 나중에 스레드 풀로 확장할 때 기존 코드를 덜어내야하는 문제가 생김.

- 왜 별도의 `room_thread` 함수를 `Room` 객체 외부에 둠?
  - 해당 `Room` 객체의 수명을 해당 `room_thread`가 들고 있는 `std::shared_ptr`로 보장하려고.
  - 적어도 해당 `room_thread`가 종료되기 전까지는 해당 `Room` 객체가 살아있어야 함.
  - 그리고, 해당 `Room` 객체 내부에 `room_thread`를 가지고 본인이 본인의 스레드 함수를 실행하면
  스레드가 실행 중일 때 다른 곳의 `shared_ptr`이 사라지면 도중에 종료되는 경우가 발생할 수 있음.
  - 그래서 `Room` 객체 외부에 해당 스레드 함수를 둠.

## 확장성을 위한 설계

미래에 스레드 풀링을 하기 전 까지는 현재 구조를 유지할 생각.
어차피 스레드 풀링을 적용하기 전에는 thread-per-object 구조를 그대로 유지하는게 억지로 갈아엎는 것보다 훨씬 생산성있다고 생각함.
(thread-per-object라는건 thread-per-client도 포함, 그 구조도 스레드 풀링 전까지는 유지할거임.)

그리고 스레드 풀링을 적용할 때는,
특정 룸에 대한 작업도 스레드 풀에 던져버리는 식으로 처리할 수 있음.
